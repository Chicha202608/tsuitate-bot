# 入力プレーンの A/B を CI の大きさで回す（Input A/B）

2026-11-22。方策ネットの入力（エンコーダのプレーン）を足したときの効果は、これまで本番の大きさ
（64ch×6・1更新 256局）で乱数初期化から 26,500〜50,000更新を GPU で数日回して確かめてきた。
これを **GitHub Actions の CPU だけで回る大きさ**に縮めて比べる道具と、その道具が信用できるかの確かめ方をまとめる。

**この大きさで入力の差が出るかどうか自体が未検証**なので、最初にやるのは答えの分かっている組での較正である
（下の「較正」）。較正が通るまでは、新しい入力の採否をこの道具だけで決めない。

## 何を回すか

腕（入力の版）× seed ごとに、小さいネットを乱数初期化から自己対局だけで育てる。学習の型は scratch の系列
（`rl_scratch_v1` / `rl_scratch5_v1`。`docs/frozen-versions.md`）と同じで、大きさだけを縮める。

| | 本番の大きさ（scratch の系列） | Input A/B |
| --- | --- | --- |
| ネット | 64ch × 6ブロック | 32ch × 3ブロック |
| 1更新の局数 | 256 | 64 |
| 更新の数 | 26,500〜50,000 | 既定 1,600（通算 約10万局） |
| 学習法 | MMD・一様な磁石・自己対局だけ | 同じ |
| 序盤 | 定跡（`rl_openings.json`）を 100% 強制 | 同じ |
| 報酬の整形 | 駒得と玉への利き（途中で切る） | 同じ重み（短いので最後まで切らない） |
| 計算 | GPU で数日 | CPU の 1スレッドで 1本 数時間。1ランナー 4本 |

腕は入力の版の名前（`v1`〜`v5`）か、`extra_arms` で足す好きな組み合わせ（`train_rnad.py` の引数）。
学習の設定の一次資料は tsuitate-nn の `rnad/input_ab.py`（`COMMON` と `ARMS`）。

## 回し方

`.github/workflows/input-ab.yml`。**通常のコード push では走らない**。

```bash
gh workflow run input-ab.yml --ref <ブランチ> -f arms="v4 v5" -f control=v4 -f treat=v5 -f seeds=8
```

`gh` が無ければ `.github/ci/input-ab.request.json` を書いて push する（例は `input-ab.request.example.json`。
削除の push は何もしない）。

| 引数 | 既定 | 中身 |
| --- | --- | --- |
| `arms` | `v4 v5` | 入力の版（スペース区切り） |
| `extra_arms` | `{}` | 追加の腕 `{"名前": "train_rnad.py の引数"}`。新しい組を試すときはここに足す |
| `control` / `treat` | `v4` / `v5` | 判定の対照と候補 |
| `seeds` | 8 | 腕ごとの本数。1ランナー 4本なので、2腕 × 8本 = 4ランナー |
| `steps` | 1600 | 通しの更新回数の上限 |
| `stages` / `stage_minutes` | 2 / 290 | 学習のジョブを何段つなぐか（1〜3）と、1段の時間。GitHub のジョブは 6時間までなので、届かなければ次の段が checkpoint から続ける |
| `export_every` | 100 | 重みを書き出す間隔（比べられる時点の刻み） |
| `games` | 100 | 総当たりの 1対の局数 |
| `horizons` | 4 | 比べる時点の数（全部の run に共通の書き出しから等間隔。最後は必ず入る） |
| `refs` | `heuristic rl_v15` | 基準の相手（絶対的な強さの目安） |
| `nn_ref` | `main` | tsuitate-nn の ref（新しい組のフラグが main に無ければそのブランチ） |

流れは plan → train1〜3（学習）→ horizons（比べる時点を選ぶ）→ crossplay（時点ごとに総当たり）→ report。
結果はジョブサマリーと artifact `input-ab-report`（表・対局の集計・入力の読み方）、学習の状態は
`iab-train-s<段>-<シャード>`（重みと checkpoint とログ。後の段ほど進んでいる）。

リポジトリは公開なので Actions の分は無料。CI のランナーでは 4本並列で 1更新 12〜18秒（学習の初めの実測。局が長くなると
遅くなる）なので、1段（290分）で進むのは 1,000更新前後。既定の設定で、学習が 4ランナー × 最長 約10時間、
対局と集計が 1〜3時間。流れだけを確かめる小さい設定（2本ずつ・30〜40更新・1段 3〜4分）は全体で 20〜26分。

## 比べ方と表の読み方

重みは `<腕>_s<seed>/current_<更新>.bin`。**同じ更新どうし**を `bin/arena` で総当たりにする
（両側とも序盤は定跡から = 学習と同じ条件。戦略名は `open:book:rl_policy:<パス>`）。対局と集計は
`scripts/ci/input_ab.py`。

| 表の数字 | 意味 |
| --- | --- |
| 腕 A の、腕 B への勝率 | A の各 seed と B の各 seed の勝率の平均 |
| かっこ内の幅 | **seed を取り直したとき**の 95% の幅（両方の腕の seed を復元抽出するブートストラップ）。1局ごとのぶれではなく「別の seed で回し直したらどれだけ変わるか」 |
| 対角（同じ腕） | seed ごとの、同じ腕のほかの seed への勝率の最小〜最大。**入力が同じでも seed だけでこれだけ散る**という目安 |
| 名札の入れ替え検定 p | 腕の名札を run の間で入れ替えても同じ差が出る確率（片側）。量は「ほかの全部の run への平均勝率」の腕ごとの平均の差 |
| 基準の相手への勝率 | 絶対的な強さの目安（腕どうしの勝率は相対的なので、両方とも弱いままでも 50% 前後になる） |
| 入力の組をどれだけ読んでいるか | その組のプレーンを 0 にして渡したときの方策の変化。**足した組をネットが読んでいなければ、勝率の差は入力のせいではない** |

判定は最後の時点で、「幅の下端が 50% を超え、かつ p < 0.05」なら候補が強い、「幅の上端が 50% 未満」なら弱い、
どちらでもなければ「この規模では分からない」。

集計の統計は差の分かっている合成データで確かめてある（8本 対 8本・1対 100局、seed ごとの強さのばらつきつき）:
差なしで「強い」と出たのは 40回中 2回、勝率 57% 相当の差で 18回、69% 相当の差で 37回。
**小さい差（勝率で 55% 前後）は 8本ずつでは半分も検出できない**ので、「分からない」は「差が無い」ではない。

## 較正（答えの分かっている組で差が再現するか）

本番の大きさでは、v5（取った駒・取られた駒の一覧つきの 124枚）は v4（102枚）より強い:
本線の相手 `rl_mmdhandex_v2` への勝率が、20,000更新で 54% 対 67.3%、26,500更新で 62.7% 対 72.3%、
直接対決でも `rl_scratch5_v1` が `rl_scratch_v1` に 62.3%。

同じ向きの差が Input A/B の大きさで出るかを、既定の設定（v4 対 v5・8本ずつ）で見る。

| 結果 | 読み方 |
| --- | --- |
| v5 が強いと出る | この道具で、同じ種類の入力（駒の一覧のように早い段階から効くもの）の採否を先に見られる |
| 分からない・逆向き | この大きさでは入力の差が見えない。更新の数を増やす（`steps` と `stages`）か、ネットを大きくするか、本番の大きさの短い比較（既存の checkpoint を広げて続ける）に戻る |

注意が 2つある。

- **小さいネットは入力を読まないことがある**。相手を固定した小さい学習で v4 の `king_fouls` を試したときは、
  組を 0 にしても方策がほとんど変わらなかった（`docs/rl-fixed-opponent.md` 8.7）。表の「入力の組をどれだけ読んでいるか」で
  毎回確かめる
- **学習の早い段階の差しか見えない**。通算 約10万局は、局数では本番の大きさの 400更新ぶんにあたる
  （小さいネットは 1局あたりの更新が多いので同じ局数でも先へ進むが、どこまで進んだかは基準の相手への勝率で見る）。
  強くなってから効く入力（終盤の読みに使うものなど）は、この道具では見えない

### 較正の結果

まだ無い。2026-11-22 に較正の run を起動した（run 45035010022。v4 対 v5・12本ずつ = 6ランナー・2,400更新まで・3段・
1対 100局・基準の相手 `heuristic` と `rl_v15`）。結果が出たらここに書く。

手元の試し（2本ずつ・300更新 = 通算 約1.9万局。本数が足りないので判定には使えない）で分かっているのは次のとおり。

| 見たもの | 値 |
| --- | --- |
| 学習が進むか | 同じ run の 100更新の重みが 50更新の重みに 67〜82%、初期値に 100% |
| 学習中の 1局の反則（片側） | 初め 7.1 → 300更新で 5.4〜6.2（まだ多くの局が反則負けで終わる） |
| 基準の相手への勝率（300更新） | `heuristic` に 100%（50更新でもう 98〜100% = 物差しにならない）、`rl_v15` に 4〜7%（飽和していない） |
| v5 対 v4（300更新・2本 対 2本） | 45.2%（幅 35.0%〜55.5%、p = 0.83）= 差は見えない |
| 入力の読み方（50更新） | 組を 0 にしたときの方策の変化: 確定事実 0.33、`opp_hand` 0.08、v5 の `lost_fresh` 0.06、ほかの組は 0.01〜0.02 |

## 手元で回す

```bash
# 学習（tsuitate-nn で。4本を並列に）
.venv/bin/python rnad/input_ab.py run --root out_rnad/iab --arms v4,v5 --seeds 1,2 --steps 300 --jobs 4 \
    --book ../tsuitate-bot/rl_openings.json --export-every 50
.venv/bin/python rnad/input_ab.py status out_rnad/iab
# 対局と表（tsuitate-bot で）
cargo build --release --bin arena
python3 scripts/ci/input_ab.py crossplay ../tsuitate-nn/out_rnad/iab --step 300 --games 100 \
    --arena target/release/arena --out /tmp/iab/step300.jsonl --refs "heuristic"
python3 scripts/ci/input_ab.py table /tmp/iab --control v4 --treat v5
```

手元（4コア）の実測: 4本並列で 1更新 8〜11秒（学習の初め。局が長くなると遅くなる）、総当たりは 200局で 18秒。
